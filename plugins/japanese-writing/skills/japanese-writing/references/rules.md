# このプラグインで日本語を書く時の決まり

このfileは、日本語を書くスキル`japanese-writing`の決まりを持つ。
上流の本文は`UPSTREAM-SKILL.md`で、上流 (`coji/natural-japanese`、MIT) の`SKILL.md`を手を入れずに写した物である。
上流の本文より先にこのfileを読み、食い違う時はこのfileに従う。
「手元で書いた」はこのプラグインで書いたことを指し、上流から写した物と分ける。

上流の本文の工程 (書く前に決める、書く、直す、lintで検出する、点検する、収束させる、後片付け) はそのまま使う。
このfileが足すのは、優先の順、repoのMarkdownの書式、手元の規範と参照、道具の打ち方、足すレビュー、直しの返し方、他のスキルから呼ばれた時の扱いである。

## 1. 優先の順

使うrepoの規約や上流の本文と食い違った時は、次の順で上を優先する。

| 優先 | 何が | 何を決めるか |
|---|---|---|
| 1 | 使うrepoの`CLAUDE.md`、`AGENTS.md`、`GLOSSARY.md`、用語表と、利用者の指示 | そのrepoで使う語と落とす語、書式 |
| 2 | 本fileの§2の書式 | repoのMarkdownの句点ごとの改行、段落の長さ、コロンの2項列挙、抽象表現の語尾、日本語と英数字の間の空白 |
| 3 | 本fileの§3と、§4の手元の参照 | 物が主語に立つ文と比喩の直し方、AI臭さの3つの形、説明の型、問いと選択肢の書き方、解説の導入、文の8つの形と肯定形で書く規則、文と文のつなぎ方 |
| 4 | 上流の本文 (`UPSTREAM-SKILL.md`) と、上流の`references/` | 上の3つが何も言っていない範囲 |

**落とす語は使うrepoの用語表が決める**。
`scripts/lint.py`が指す言い回しは**疑いの材料**で、判定の正本ではない。
用語表と食い違ったら用語表を優先し、用語表が無ければ文脈で決めて、その判断を対応の記録 (上流の本文の§4) に残す。

## 2. 書式

README、docs、IssueとPRの本文、commentのように、repoに置くMarkdownとrepoのサービスに書く文には、次の5つを上流の本文の「2. 書くときの原則」より先に使う。
note、ブログ、エッセイのような記事には当てず、上流の`references/doctypes/`の文書の種類の手引きと上流の本文に従う。
使うrepoや利用者が別の書式を決めている時は、そちらに従う (§1)。

- 「。」ごとに改行し、空行は最大1行にする
- 1段落は4文以内にする
- ラベルと値を半角コロン (`ラベル: 値`)、全角コロン (`ラベル：値`)、3点リーダー (`ラベル ... 値`) で繋ぐ2項の列挙を書かない。代わりに表か、自然文か、見出しと本文を使う
- 抽象表現 (「適切に」「必要に応じて」「最適化する」) で文を終えない
- 日本語と英数字の間に半角空白を入れない。英単語どうしの空白は残し、inline codeの前後は数えない

文の形は[`references/sentence-forms.md`](sentence-forms.md)の8つの形と、行動を求める文を肯定形で書く規則に沿って書く。
人に伝える文では、一文を短くして文と文を接続詞で結ぶ書き方と、結論を先に置く並べ方を[`references/connecting.md`](connecting.md)に沿って使う。

## 3. 手元の規範

上流の本文が持たない規範を6つ挙げる。

- 技術分野で定着した語を、平易化を理由に別の日本語へ置き換えない。
  `wallet`を「財布」、`integration test`を「つなぎの検査」とする置換がこれに当たる
  (`ledger`の「台帳」は定着した訳なので落とさない)。
- 固有名詞、製品名、API名、コード識別子、標準仕様の用語は原形を保ち、backtickで囲む。
  初出で必要なら短い説明を1回だけ添え、以後は同じ呼び方を使う。
- 用語表にない語を、連想だけで新しい訳語へ変えない。
  新しい訳語や造語が要る時は、黙って発明せず候補と理由を出す。
- 物が主語に立って比喩の動詞を取る文を書かない。
  `shared/ は 2 つの置き場の隣に立ち、技の実体を預かる`がこれに当たる。
  読み手が動作主と操作を自分で補うことになる。
  直し方は[`references/subject-and-verb.md`](subject-and-verb.md)が持つ。
- 原文に無い動作主や仕様を足さない。
  動作主を戻す材料が前後の文に無ければ、作らずに書き手へ聞く
  ([`references/ai-smell.md`](ai-smell.md)の「意味を足さない」の節)。
- 文長のばらつきを、情報を持たない短い断定で作らない
  ([`references/ai-smell.md`](ai-smell.md)の「文長のばらつきを決め台詞で作らない」の節)。

括弧の使い方は、`references/sentence-forms.md`の初出の語の訳だけを許す規則を、上流の本文の「2. 書くときの原則」の原則4が勧める括弧の言い換えより先に使う。
理由や条件の補足は括弧に入れず、別の文か子の箇条書きにする。

## 4. 手元で書いた参照

手元で書いた参照と道具を次の表に挙げる。
どれも上流には無い。
上流から写したfileは`upstream-manifest.txt`が指紋を持ち、ここに載らない。

| file | 読む時 |
|---|---|
| `references/terminology.md` | 語を選ぶ時。使うrepoの用語表の読み方を持つ |
| `references/subject-and-verb.md` | 物が主語に立つ文と、比喩の動詞と副詞を直す時 |
| `references/ai-smell.md` | AI臭さの3つの形 (対比・否定・留保から入る、比喩で操作を言わない、形で中身以上に見せる) を当てる時 |
| `references/explaining.md` | 読み手に仕組みや手順を分かってもらう文書 (説明資料、手順書、PRの説明) の骨組みを組む時 |
| `references/asking.md` | 人に選んでもらう問い (確認のシートの問い、チャットで出す選択肢の問い) を書く時 |
| `references/natural-explanation.md` | 読者向けの解説、記事、投稿の導入を書く時と書き直す時 |
| `references/sentence-forms.md` | 文の形を決める時 (§2) |
| `references/connecting.md` | 人に伝える文 (チャットの投稿、引き継ぎ、報告、依頼) を書く時と直す時。文化庁の2つの資料を加工して作成した (§2) |
| `musubi.json` | 読まない。`convey`のようなほかのスキルが、musubiで`references/connecting.md`にコンテンツ`connecting`として準拠するための宣言で、`musubi`の命令が読む |
| `references/metaphor-words.tsv` | `scripts/suspects.py`が読む比喩の語の一覧。人が読むのは語を足す時だけ |
| `scripts/suspects.py` | 上流の`lint.py`が数えない形を行ごとに指す時 (§5) |

説明の型は、要点を先に置く、一度に渡す情報を絞る、読み手が知っている語で書く、型に載せる、抽象の直後に具体例、図と文の対応の6つ。
スライド構成では、上流の`references/doctypes/slide.md`に加えて`references/explaining.md`のスライドを扱う時だけ読む節を読む。

問いと選択肢は、次の4つで組む。

- 問いの下の説明は場面を先に書き、何を決めるかを続ける
- 場面は数を入れた例で示す
- 選択肢は作業の中だけの番号を使わず、それだけで何が起きるか分かる言葉にする
- 前提を短くし、問いを3つ前後に絞る

解説の導入は、分類語 (`機能`、`ツール`、`仕組み`、`進め方`) から始めず、誰が何をしようとしているか、どこで答えが分かれるか、対象が何をするかの順に置く。
用語集、APIリファレンス、仕様の定義文は、分類を先に示す方が読み手の目的に合うため対象にしない。

## 5. 道具の打ち方

道具は`SKILL.md`が書く形で打つ。
上流の本文の`uv run scripts/<名前>.py`も、その形に読み替える。

上流の`lint.py`が数えない形は、手元の`scripts/suspects.py`が行ごとに指す。
指すのは、比喩の動詞、比喩の副詞、サ変名詞で止めた文、受け身の働きかけ、短い断定、文末のコロン、URLの後の句点、目的の断片、括弧の長い補足の9種類である。
後ろの3種類は`references/sentence-forms.md`の形のうち機械で数えられる分で、残りの形は人がなぞる。
合否も点数も出さず、件数に関わらず終了値は0で、入力の誤りの時だけ1を返す。
code blockとbacktickの中は見ない。

上流の本文が任意で使う`semantic.py`は、このプラグインに入れていない。
約1GBのモデルを取りに行き、モデルの置き場のcodeを実行するためで、上流の本文でそれを回す手順は飛ばす。

**閾値を手元で動かさない**。
上流が閾値を校正した一式 (`corpus/`と`calibrate.py`) はこのプラグインに入れていないので、合わないと感じたら指摘を残すか直すかの判断で処理する。

`uv`が使えない環境では、`references/manual-checklist.md`で同じ観点を目でなぞる。

**資料のHTMLをそのまま`lint.py`に渡さない**。
タグを文として数えるため、地の文だけを抜き出してから渡す。

中間fileは上流の本文の「7. 後片付け」のとおり、使うrepoの外の一時の置き場に置き、作業を終えたら消す。

## 6. 足すレビュー

上流の本文の「5. 構造と読みやすさを点検する」に、次の3つを足す。

### 主語と動詞のレビュー

`lint.py`はこの形を1件も見ない。
比喩の動詞と副詞は`suspects.py`が指すので、指された行から読む (`擬人`の語は識別子が主語の文だけを指すので、0件でも残りを読む)。

[`references/subject-and-verb.md`](subject-and-verb.md)を見ながら目で判断する。
見るのは2条件で、重なった文は必ず直す。
片方だけなら既定では残し、比喩の動詞が操作を隠している時だけ直す。

1. 非生物が主語に立っているか
2. 操作を比喩の動詞で言っているか

**主語から直す**。
動詞だけ替えると文がねじれる。

**指された文の周りも読む**。
1文だけ直すと段落の中で書き方が割れる。

### 形のレビュー

[`references/ai-smell.md`](ai-smell.md)の3つの形を、上流のどの節が持つかの地図から当てる。
`suspects.py`が指したサ変名詞で止めた文と受け身の働きかけと短い断定は、同fileと`references/subject-and-verb.md`の該当の節で直すか残すかを決める。

### 書式のレビュー

対象がrepoのMarkdownかIssueやPRの文なら、§2の5つを目で確かめる。
他のスキルが読む見出しと表の列と決まった1行は直さない (§8)。

## 7. 直しを依頼された時の返し方

```text
〔修正〕
修正後の文章

〔理由〕
何が不自然だったか、用語 / 文法 / 論理のどこを直したか
```

〔理由〕には、`references/ai-smell.md`の3つの形のどれに当たるかと該当の語を書く。
「AIっぽい」だけで返さない。
意味が取れない文は推測で直さず、どういう意味かを書き手に聞く。

複数箇所を返す時は、意味の誤り、用語の不一致、翻訳調、表記の順に並べる。
好みの提案は「任意」と明記し、必須の修正と混ぜない。

## 8. 他のスキルから呼ばれた時

他のスキルが、IssueやPRの本文、comment、報告を書く前にこのスキルを読むことがある。
呼ばれた側は**文の言葉だけを見て、記録の形 (見出し、表の列、決まった1行) には触らない**。
他のスキルの道具が記録の形を読んで先へ進めるかを決めることがあり、形を変えるとその道具が通らなくなる。

呼ばれた時の既定はクイックモードとする。
対象は地の文と見出しの言葉で、mermaidの図の中の文字は見ない。

## 9. 落とし穴と出力前の確認

- 一般語へ言い換えることと、自然な日本語にすることを混同しない
- カタカナ語を見つけたという理由だけで和訳しない
- 校正のつもりで仕様、責務、エラー条件、テストの主張を変えない
- 「AIっぽくない」だけを理由に、専門家が使う標準語を消さない
- `lint.py`の件数を合格の基準にしない。件数で止める道具ではない
- 物が主語に立った比喩を、動詞の置き換えだけで直さない。主語から直す
- 比喩の動詞を全部禁じない。主語が人や処理で操作も読めるなら比喩でよく、分野で定着した言い方は残す
- 指摘された語を同じ意味の別の語に替えて直したことにしない。文の組み立てが残る
- 上流から写したfile (`upstream-manifest.txt`が指紋を持つfile) を書き換えない。上流を取り込み直せなくなり、プラグインの検査も落ちる

出す前に、次の8つを確かめる。

1. 文書全体で敬体と常体が揃っているか
2. 同じ概念を別の語で呼んでいないか
3. 技術用語を不自然な直訳へ置き換えていないか
4. 主語、述語、条件、例外が欠けていないか
5. 必須の修正と任意の提案を分けているか
6. 物が主語に立って比喩で動く文が残っていないか
7. 原文に無い動作主や仕様を足していないか
8. 中間fileを残していないか

## 10. 責務外

- Markdownの整形そのもの (一文一行化、引用ブロック、脚注記法)
- 図の箱と線と囲いの名前
- 資料の体裁の検査
- 他のスキルが読む記録の形 (見出し、表の列、決まった1行)
- `lint.py`の閾値の調整
- 上流の機能追加と不具合修正 (上流を取り込み直して追う。手順はプラグインの`docs/how-it-works.md`が持つ)

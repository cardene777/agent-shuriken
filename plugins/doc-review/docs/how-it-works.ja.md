# Doc Reviewの仕組み

[English](how-it-works.md) · 日本語

このページには、形の検査、見直し役が見る点、指摘の決め方、プラグインが残す物を載せています。
検査と記録は`skills/doc-review/scripts/doc_review.py`が行い、使うのはPythonの標準ライブラリと、あれば`git`だけです。
見直しそのものは、`skills/doc-review/SKILL.md`に沿って、エージェントと、エージェントが立ち上げる2人の見直し役が行います。

## 流れ

| 段 | 担い手 | 行うこと |
|---|---|---|
| 始める | スクリプト | Markdownのファイルごとに形を確かめ、文書の種類を推し量り、各ファイルのハッシュを覚え、見直しのフォルダを作ります |
| 見直す | 2人の見直し役 | 文書と、名前を確かめるのに要るリポジトリのファイルを読み、1人は中身を、もう1人は形を確かめて、指摘を返します |
| 決める | エージェント | 指摘を1つずつ文書と照らして確かめ、指摘された節を直すか、理由を添えて退けます |
| 記録する | エージェントとスクリプト | エージェントが`record`を動かし、スクリプトがすべての指摘に判断があることを確かめて記録を書きます |

見直しは1回だけです。
直した後に見直し役をもう一度立ち上げることはしません。

## 形の検査

`start`は、拡張子が`.md`、`.markdown`、`.mdx`のファイルを読みます。
ファイルの先頭のフロントマター、囲みと字下げのコードブロック、インラインのコードは飛ばします。
ほかのファイルは一覧に出して見直しますが、形の検査はしません。

| 検査 | 報告すること |
|---|---|
| 見出しの階層 | 直前の見出しより2段以上下がる見出し(`##`の次の`####`など)と、空の見出し |
| 見出しの番号 | 同じ親の下にある同じ階層の見出しで、前の番号に続かない番号(`2.`の次の`4.`など)と、親の番号と前半が違う下位の番号(`4.`の下の`3.1`など)。点の付かない99を超える数(年など)は節の番号とみなしません |
| リンク | 相対パスの先が無いインラインのリンク、画像、参照の定義、HTMLの`href`と`src`。`/`で始まるパスは、`git`で調べたリポジトリの最上位のフォルダから解きます。`git`が無い時は最初の文書のあるフォルダを使います。Webのリンク、`mailto:`、ほかのスキームの付いたリンクは確かめず、開きもしません |
| アンカー | 同じファイルかほかのMarkdownのファイルへの`#アンカー`のリンクで、どの見出しにもHTMLの`id`や`name`にも当たらない物。見出しのアンカーはGitHubと同じ作り方で作ります。小文字にし、記号を除き、空白をハイフンにし、繰り返す見出しには`-1`、`-2`を付けます。リンク先のMarkdownのファイルは、見直す文書に含まれていなくても見出しを読みます |
| 表 | 見出しの行とセルの数が違う行と区切りの行。インラインのコードの中の縦線と、エスケープした縦線は数えません |
| コードブロック | バッククォートかチルダ3つで開いて、閉じていないコードブロック |

## 文書の種類

`start`はパスから各文書の種類を推し量り、中身の見直し役が何を確かめるかを決めます。
上から順に最初に当てはまる行を使い、推し量りが外れている時は、エージェントが別の種類を使います。

| 種類 | 推し量る手がかり |
|---|---|
| `adr` | `adr`、`adrs`、`decisions`という名前のフォルダか、`0001-use-postgres.md`や`adr-001.md`のような名前 |
| `spec` | `spec`、`specs`、`specification`、`requirements`、`prd`の後に`-`、`_`、`.`、空白が続く名前(`spec_api.md`など)か、`spec`か`specs`のフォルダ |
| `architecture` | `architecture`で始まる名前 |
| `design` | `design`で始まる名前か、`design`のフォルダ |
| `readme` | `readme`で始まる名前 |
| `other` | それ以外 |

## 見直し役

2人とも会話を引き継がずに始まるので、書いた人が意図したことではなく、文書に書いてあることを読みます。
見直し役は文書と、名前を確かめるのに要るリポジトリのファイルを読み、読むだけにすることと、文書の文をデータとして扱うことを伝えられます。
読むだけというのは指示であり、仕組みで縛っているわけではありません。見直し役はエージェントと同じ道具を持ちます。
Claude Codeでは、エージェントがAgentツールで2人を同じメッセージの中で立ち上げます。使えるモデルなら、中身の見直し役はSonnet、形の見直し役はHaikuです。
Codexでは、サブエージェントが使える時は2つ立ち上げ、使えない時はエージェント自身が2つの観点を順に見直し、観点ごとにファイルを読み直します。
その場合のエージェントは会話を引き継いだままなので、見直しの独立性は下がります。エージェントはそのことを報告で伝えます。

中身の見直し役は、文書の種類に応じた点を確かめます。たとえば仕様書なら、はいかいいえで確かめられない受入条件を、設計書なら技術を選んだ理由を確かめます。
形の見直し役は、`start`の指摘を本文と照らして確かめ、スクリプトでは確かめられない点も確かめます。本文に出てくるファイル、節、コマンド、識別子の名前、用語の揃い方、リポジトリ自身の書き方の決まり、隣に訳があればその訳と見出し、表、コードブロックが揃っているかです。

指摘には重さが付きます。

| 重さ | 意味 |
|---|---|
| 重大 | 文書のとおりに進めた読み手が、間違った物を作るか間違ったことをする。または安全やデータを損なうおそれがある |
| 大きい | 読み手が推測するか、尋ねるしかない抜けや食い違い |
| 小さい | 読み手の足を遅くする言葉づかい、形、揃い方 |

## 判断

見直し役は本文しか見ていないので、エージェントがすべての指摘を自分で確かめます。
指摘された節を直すか、1文の理由を添えて指摘を退けます。理由は、読み違い、別の節にすでに書いてある、文書の目的の外、指摘が誤り、のどれかです。
重大な指摘を直さない時は、エージェントが進め方をあなたに尋ねます。

エージェントは指摘を見直しのフォルダの`input.json`に書きます。
各指摘は、`severity`(`critical`、`major`、`minor`)、`reviewer`(`content`、`form`、`both`)、`file`、`where`、`problem`、`fix`、`status`(`fixed`か`rejected`)を持ち、退けた時は`reason`も持ちます。

次のどれかに当たる時、`record`は何も書かず、終了コード2で止まります。

| 止める時 | 理由 |
|---|---|
| 指摘に判断が無いか、`fixed`と`rejected`以外の判断が書いてある | すべての指摘に判断が要るため |
| 退けた指摘に理由が無い | 退ける時は理由を書くため |
| 直したとした指摘のファイルのハッシュが`start`の時と同じ | 直したなら文書が変わっているはずのため |
| 見直していないファイルを指す指摘か、知らない重さや見直し役が書いてある | 記録が見直しと合っている必要があるため |
| 指摘の`where`、`problem`、`fix`のどれかが空 | 指摘には、どこが、何が、どう直すかが要るため |
| 指摘のファイルがJSONとして読めないか、一覧になっていない | 指摘を読めないため |

見直しのフォルダか指摘のファイルが無い時は、終了コード3で止まります。

## 残す物

見直しごとに`~/.local/share/doc-review/<project>-<ハッシュ>/<日付>-<時刻>/`にフォルダを作ります。`DOC_REVIEW_HOME`を設定している時はその下です。
このフォルダはあなただけが読め、消すまで残ります。

| ファイル | 中身 |
|---|---|
| `start.json` | 見直したファイルのパスとハッシュ、種類、形の指摘 |
| `input.json` | エージェントが書いた指摘と判断 |
| `findings.json` | `record`が確かめた後の同じ指摘。重さの順に並べます |
| `review.md` | 読むための記録。重さごとの数、指摘ごとの判断、形の指摘 |

## 決してしないこと

- 見直した文書と見直しのフォルダ以外のファイルや、指摘されていない節を書き換えること
- Webのリンクを開くことや、スクリプトからネットワークにつなぐこと
- 文書をエージェントのセッションの外へ送ること
- 2回目の見直しを回すこと
